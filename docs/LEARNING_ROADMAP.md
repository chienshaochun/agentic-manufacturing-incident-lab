# 教學式實作路線圖

## 學習節奏

每個小階段都使用相同節奏：

1. 先解釋概念與物理意義。
2. 只實作一個可觀察的新能力。
3. 以測試或手動操作證明它有效。
4. 將單一目的的變更 commit。
5. 說明結果、限制與下一階段的連接方式。

大階段完成並驗證後才 push 到 GitHub。這能讓 Git 歷史同時成為學習紀錄。

## Phase 0：問題與邊界

建立 README、產品契約與學習路線圖，明確定義輸入、輸出、不做事項和成功標準。

物理意義：先畫出廠區、權限和驗收表，避免設備還沒定位就開始拉線。

## Phase 1：領域模型

用 Python 型別表示事件、觀察、動作、證據、任務狀態與執行結果，並建立狀態轉換測試。

物理意義：替現場所有單據與訊號建立一致格式，讓不同角色不會把「告警」、「量測」和「處置」混為一談。

## Phase 2：模擬世界與工具

建立可重播情境、工具登錄表、唯讀診斷工具與固定 workflow baseline。

物理意義：搭建訓練用產線與儀表板；我們能製造已知故障，才能判斷調查方法是否真的找到答案。

## Phase 3：單 Agent 決策循環

實作 observe-plan-act-reflect-stop 循環，先使用確定性的規則策略，之後才提供模型策略介面。

物理意義：值班主管開始依現場回報選擇下一個量測，而不是照固定清單從頭做到尾。

## Phase 4：任務、記憶與檢查點

追蹤已知事實、未解問題、步驟預算與序列化檢查點，使中斷任務能恢復。

物理意義：建立交班白板與值班紀錄，換人或系統重啟後不必重新調查。

## Phase 5：批准、安全與故障恢復

加入工具白名單、風險分級、人工批准、逾時、重試、替代路徑與安全停止。

物理意義：加入門禁、聯鎖與緊急停止；主管可以調查，但高風險動作不能自行越權。

## Phase 6：多 Agent 協作

拆分協調、診斷、安全審查與報告角色，定義結構化交接，並與單 Agent baseline 比較。

物理意義：由單一值班主管擴充成專責小組，但每次交接都必須附上證據與責任範圍。

## Phase 7：評估、故障注入與可觀測性

建立 benchmark、故障注入、軌跡檢視與量化指標，檢查結果是否可重現。

物理意義：不是看演練是否順眼，而是定期投入已知故障，量測反應時間、誤動作與恢復能力。

## Phase 8：Streamlit 與手動演示

製作情境選擇、逐步執行、批准操作、軌跡檢視與報告匯出的展示介面，完成端到端手操。

物理意義：把控制室、批准面板和交班報告整合成可供面試展示的操作台。

## Phase 9：Hypothesis Engine

建立競爭故障假設、支持與反對Signal、狀態評分、checkpoint保存及UI呈現。

物理意義：在調查白板列出所有候選原因，每次量測都要說明排除了什麼、保留了什麼，而不是只記錄最後答案。

## Phase 10：動態工具選擇

依假設資訊價值、操作風險、成本、重複呼叫與Action budget選擇下一個Tool。

## Phase 11：真實感製造情境

加入Alarm history、設備設定、維護紀錄、Sensor freshness與多個可能根因。

## Phase 12：Structured LLM Planner

新增可選配的結構化LLM策略，並保留Tool白名單、Schema驗證、安全政策與Rule-based fallback。

## Phase 13：Agent能力評估

增加假設解決率、無依據主張率、重複Tool率、Evidence所需Action數與恢復成功率。

完成狀態：已完成，並加入五個 connectivity cases 的 Planner A/B Dashboard。各指標的計算與限制見 [Phase 13 說明](PHASE_13_AGENT_EVALUATION.md)。

## Phase 14：Evidence 品質與不確定性

替 Observation 加入來源可靠度、量測品質與新鮮度，讓支持與反對訊號依品質加權；再以跨來源需求區分「同一來源重複說了兩次」和「兩個獨立系統互相佐證」。若高品質訊號互相衝突、資料品質不足，或同時支持多個原因，調查必須安全停止。

物理意義：現場不只要看儀表讀到什麼，也要確認儀表是否可信、資料是否過期，以及另一套獨立系統能否交叉驗證。

完成狀態：已完成；完整設計與三個不確定案例見 [Phase 14 說明](PHASE_14_EVIDENCE_QUALITY.md)。

## Phase 15：症狀導向操作台與推理可視化

將使用者輸入的症狀與 benchmark answer key 分離，並呈現每一步 Observation 如何改變各候選 Hypothesis、哪些訊號支持或反對，以及 Planner 為何選擇下一個 Tool。

物理意義：操作員只回報看得到的異常；系統在白板上逐步更新候選原因，而不是先把標準答案放進下拉選單。

完成狀態：已完成；見 [Phase 15 說明](PHASE_15_INVESTIGATION_UX.md)。

## Phase 16：結構化 Incident Intake

在自然語言模型之前先建立嚴格 Schema、Parser 介面、手動 fallback 與操作員確認閘門。只有通過型別、欄位、設備範圍與症狀 allowlist 驗證的資料才能進入 Agent 流程。

物理意義：先建立標準報修單與簽名確認流程，再讓語言模型協助填表；模型不能自行新增欄位、宣告 Root Cause 或繞過操作員。

完成狀態：已完成；見 [Phase 16 說明](PHASE_16_STRUCTURED_INCIDENT_INTAKE.md)。

## Phase 17：Ollama Structured Parser

讓本機 Ollama 只負責把操作員文字轉成 Phase 16 Schema，並加入逾時、格式錯誤、低信心 fallback 與模型／人工結果比較。此階段暫緩，等確認本機硬體、模型大小與部署模式後再實作。

## 技術採用順序

- 核心先使用 Python 3.12 與標準函式庫，保持行為透明。
- 測試使用 pytest；格式、型別與 CI 在核心建立後加入。
- UI 最後使用 Streamlit，避免畫面掩蓋尚未完成的 Agent 能力。
- LLM 只透過策略介面接入；本機 Ollama 或 API 都是可選配，不影響 deterministic 測試。

## 預期學會的能力

- 分辨固定 workflow 與真正的 Agent 決策
- 設計工具契約、狀態機、記憶與停止條件
- 對 Agent 加入最小權限、人工批准與可恢復執行
- 使用可重播情境與指標評估，而非只看展示結果
- 解釋多 Agent 的必要性、成本與失敗模式
- 將 Agentic AI 系統清楚呈現在程式碼、測試、UI 與面試敘事中
